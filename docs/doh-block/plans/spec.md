# DoH 차단 - 명세

## 화면/기능 흐름

- 차단 구간 진입 (막을 사이트가 하나 이상): 데몬이 `hosts` 블록을 쓰고, 같은 tick에서 시스템 네임서버 IP의 443을 막는 PF 앵커를 적용 → 브라우저가 DoH로 승격하지 못하고 시스템 리졸버로 되돌아가며, hosts가 먹는다
- 차단 구간 이탈 (막을 사이트 없음): `hosts` 블록 제거 + PF 앵커 비우기 + `pf.conf` 마커 줄 제거 + `pfctl -X <토큰>`
- 시스템 DNS 변경 (공유기 교체, Wi-Fi 전환): 다음 tick에서 `scutil --dns`를 다시 읽어 앵커 내용이 달라지면 새로 로드. 같으면 아무것도 하지 않는다
- `pf.conf`가 순정으로 되돌아감 (macOS 업데이트): 다음 tick에서 마커 줄이 없는 걸 보고 다시 넣는다
- 데몬 제거: 제거 스크립트가 부르는 `--clear`가 hosts와 PF를 함께 되돌린다
- 앱 설정 열기: 데몬이 남긴 `/Library/Application Support/Break/pf.status`를 앱이 읽어 한 줄로 보여준다. `ok`면 "보안 DNS 차단: 적용 중", 다른 내용이면 "보안 DNS 차단: 실패", 파일이 없으면 줄을 감춘다. 해제가 실패하면 파일에 실패 메시지가 남으므로 그때도 화면에 뜬다

## 상태 정의

| 상태 | 설명 |
| --- | --- |
| 미적용 | 차단 구간이 아니거나 막을 사이트가 없음. PF 앵커는 비어 있고 `pf.conf`에 Break 줄이 없다 |
| 적용 중 | 앵커에 네임서버 IP별 443 차단 규칙이 올라가 있고 PF가 켜져 있다 (토큰 보유) |
| 적용 실패 | `pf.conf` 수정이나 `pfctl` 호출이 실패. hosts 차단은 그대로 살아 있고, DoH만 안 막힌 상태 |
| 대상 없음 | `scutil --dns`가 네임서버를 하나도 못 주거나 루프백뿐. 막을 것이 없으니 미적용과 같게 둔다 |

## 엣지 케이스

- **PF가 이미 켜져 있음**: `pfctl -E`는 참조 카운트를 올리고 토큰을 준다. 우리 토큰만 반납하므로 다른 앱이 켜 둔 PF는 그대로 남는다. 절대 `pfctl -d`를 부르지 않는다
- **토큰 파일이 사라짐**: 반납할 토큰을 모르면 PF를 끄지 않고 앵커만 비운다. 켜진 채로 남는 편이 남의 PF를 내리는 것보다 안전하다
- **SelfControl이 동시에 동작**: 서로 다른 앵커를 쓰므로 규칙끼리는 안 부딪힌다. 다만 상대가 `pfctl -f /etc/pf.conf`로 메인 룰셋을 다시 읽으면 우리 앵커 줄이 사라질 수 있다 — 다음 tick에서 되살린다
- **`scutil --dns`가 빈 결과를 줌**: `/etc/resolv.conf`의 `nameserver` 줄을 폴백으로 읽는다. 둘 다 비면 "대상 없음"이다. 폴백이 없으면 이 기능 전체가 아무 표시 없이 무효화된다
- **네임서버가 루프백**: `127.0.0.1` / `::1`은 규칙에서 뺀다. 넣으면 로컬 443 서비스가 막힌다
- **네임서버가 사설 대역 공유기 IP** (예: `192.168.0.1`): 그대로 막는다. 공유기는 DoH 엔드포인트가 아니므로 443을 막아도 DNS(53번)는 멀쩡하다
- **막을 사이트는 있는데 PF 적용 실패**: hosts 차단은 유지한다. DoH 가드만 실패로 두고 화면에 올린다. 전부 포기하지 않는다
- **`pf.conf` 수정 권한 없음**: 데몬은 root라 정상 상황에서는 안 난다. 나면 `Outcome::Failed`로 로그에 남기고 앱에 올린다
- **브라우저가 보안 DNS를 "사용"(strict)으로 직접 켜 둠**: 이 방식으로는 못 막는다. 자동 모드의 승격만 끊는다. 알려진 한계로 두고, 필요하면 제공자 IP 목록을 나중에 얹는다
- **VPN 사용 중** (Cloudflare WARP 등): `hosts`는 네트워크에 나가기 전 단계에서 읽히고 PF는 터널로 나가는 패킷도 본다. 그래서 원리상 우회되지 않는다. 다만 VPN 클라이언트마다 DNS를 가로채는 방식이 달라 실제로 켜 보기 전에는 알 수 없다 — 확인되지 않은 상태로 둔다

## Chromium은 hosts를 안 본다

`/etc/hosts`는 OS 리졸버가 지키는 규칙이다. Chromium 계열(Chrome, Arc, Dia, Aside, Whale)은 OS에
이름을 묻지 않고 자체 DNS 클라이언트로 직접 물어보며, 이때 hosts는 적용되지 않는다. DoH를 막아도
평범한 DNS로 내려갈 뿐이라 같은 결과다. Safari만 OS 리졸버를 써서 hosts로 막힌다.

그래서 Chromium에는 관리형 정책의 `URLBlocklist`를 쓴다. 브라우저가 주소 단계에서 거부하므로
DNS를 아예 타지 않고, 캐시·DoH·자체 리졸버가 모두 무관해진다. 서브도메인은 한 줄로 함께 덮인다.
정책은 브라우저를 껐다 켜야 반영된다 — 차단 시작 때 브라우저를 닫는 기존 흐름과 맞는다.

`/Library/Managed Preferences/<번들ID>.plist`에 쓰고, 우리가 쓴 파일에는 `BreakManaged` 키를 남긴다.
그 키가 없는 파일은 다른 곳(MDM 등)이 관리하는 것이므로 읽고 지나간다 — 덮어쓰지도, 지우지도 않는다.

> 2026-09-03 실측 정정 (`docs/block-layers/plans/spec.md`): "Chromium 계열은 hosts가 안 먹는다"는
> 브라우저마다 다르다. hosts + PF만 걸었을 때 Chrome과 Safari는 막혔고 Aside만 뚫렸다. 즉
> `URLBlocklist`가 실제로 값을 하는 대상은 지금 확인된 범위에서 Aside 한 곳이다. 그래도 계층은
> 유지한다 — 브라우저가 자체 경로로 IP를 얻는 순간 hosts와 PF는 둘 다 지나가기 때문이다.

## 막지 않는 것

이 기능이 닫는 구멍은 **아무 조작 없이 저절로 뚫리는 경로 하나**다. 아래는 이번에도, 앞으로도
막을 계획이 없다. 나중에 "왜 안 막지"로 다시 파지 않도록 적어 둔다.

| 우회 방법 | 필요한 것 | 이 기능으로 막히나 |
| --- | --- | --- |
| 그냥 접속 | 없음 | 막힘 (`hosts`) |
| 브라우저가 알아서 DoH로 승격 | 없음 — 저절로 일어난다 | **이번 작업으로 막힘** |
| 브라우저 설정에서 보안 DNS 직접 켜기 | 클릭 몇 번 | 막힘 — `URLBlocklist`는 DNS를 거치지 않는다 |
| 커스텀 DoH 주소 직접 입력 | 주소를 알아야 함 | 안 막힘 |
| `sudo`로 Break를 지움 | 관리자 암호 | 안 막힘 |

마지막 줄이 근본 한계다. 설치할 때 이 Mac의 관리자 암호를 입력했으므로, 작정하면 무엇을 넣어도
지울 수 있다. 이 도구가 이기려는 상대는 작정한 사용자가 아니라 습관적으로 손이 가는 사용자다.
