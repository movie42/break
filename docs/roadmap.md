# Break 청사진

앞으로 무엇을 만들지와 왜 그 순서인지를 적어 둔 문서. 실행 계획이 아니라 방향이다.
실제 작업은 착수할 때 `docs/<이름>/plans/`에 따로 만든다.

작성: 2026-08-31

## 지금 서 있는 자리

차단 파이프라인이 끝에서 끝까지 연결돼 있다. 앱에서 사이트와 시간대를 넣으면 그 시각에
브라우저에서 실제로 열리지 않는다. Safari, Chrome, Aside에서 확인했다.

| 크레이트 | 하는 일 |
| --- | --- |
| `break-core` | 규칙 타입, 시간대 판정(자정 넘김 포함), JSON 입출력, 깨진 파일 격리, v1 파일 이행 |
| `break-enforcer` | `/etc/hosts` 마커 블록 생성·제거, DNS 캐시 비우기 |
| `break-daemon` | root로 상주. 1초마다 규칙을 다시 읽고 `hosts`를 맞춘다 |
| `break-app` | Tauri 커맨드, 트레이, 데몬 설치·제거 |

화면은 시간대 / 사이트 두 탭. 창을 닫으면 트레이로 들어간다.

사이트는 **그룹**으로 묶고 시간대가 그룹을 지목한다. 어느 시각에 막히는 주소는 그때 켜져 있는
시간대들이 지목한 그룹의 합집합이다. v1 파일은 여는 순간 그룹 하나로 접힌다 —
`docs/redesign/rules-v2.md`.

규칙 파일은 v3이다. 시간대마다 `enabled`가 있어서 만드는 것과 실행하는 것이 갈라졌고,
실행 중인 시간대는 끄거나 지울 수 없다 — `docs/redesign/rules-v3.md`.

지난 작업 문서는 `docs/initial-setup/plans/`와 `docs/site-blocking/plans/`에 있다.

## 만들 것

굵은 순서대로. 번호가 곧 우선순위는 아니고, 아래 "어떤 순서로"에서 다시 정리한다.

### 1. 앱 차단

제품으로서 가장 큰 구멍이다. 이 앱의 이름은 "사이트 차단기"가 아니고, 상태 화면은 이미
"차단 앱 N개"를 세고 있는데 넣을 방법이 없다. 규칙 타입(`AppTarget`)과 저장은 이미 되고,
`apply_apps`가 `NotPrivileged`를 반환하는 상태로 남아 있다.

어려운 지점 세 가지:

- 설치된 앱과 실행 중인 앱 목록을 어떻게 가져올지 — `/Applications` 스캔과 실행 중 프로세스 조회는 서로 다른 일이다
- 번들 ID(`com.apple.Safari` 같은 앱의 고유 이름)를 사용자에게 어떻게 고르게 할지
- 프로세스를 주기적으로 종료하는 방식이 맞는지. 사용자가 저장하지 않은 작업이 날아갈 수 있다

### 2. 차단 중이라는 안내

지금은 사이트가 그냥 열리지 않는다. 브라우저가 "연결할 수 없음"을 띄우고, 사용자는 Break가
막은 것인지 인터넷이 끊긴 것인지 모른다.

`hosts`가 이미 `127.0.0.1`(자기 컴퓨터)로 보내고 있다. 데몬이 그 자리에 작은 웹 서버를 띄우면
브라우저에 "Break가 막고 있습니다. 19:00에 풀립니다" 같은 페이지를 보여줄 수 있다. 필요한
정보는 데몬이 이미 다 들고 있다.

비용 대비 체감이 가장 크다. 다만 HTTPS는 인증서가 없어 경고 화면이 뜬다 — HTTP만 되고,
요즘 사이트는 대부분 HTTPS라 실제로는 절반만 먹는다. 착수 전에 이 한계부터 재봐야 한다.

### 3. 시간대 편집

만들고 지우는 것만 된다. 22:00~02:00을 22:30~02:00으로 고치려면 지우고 다시 만들어야 한다.
작지만 매번 걸린다.

### 4. 트레이에서 보이는 상태

메뉴가 "열기 / 종료" 둘뿐이다. 지금 차단 중인지, 언제 풀리는지가 트레이에서 안 보인다.
창을 열지 않고 확인할 수 있어야 상주 앱답다.

### 5. 배포

코드 서명이 없어서 `.app`을 만들어도 다른 Mac에서 열리지 않는다. Apple Developer Program
가입(연 $99)이 전제다. 이게 풀리면 `SMAppService`도 같이 풀려서, `osascript`로 암호를 받는
지금 방식을 Apple 권장 방식으로 바꿀 수 있다.

### 6. Windows

`WindowsEnforcer`가 전부 스텁이다. Windows 머신 없이는 서비스 설치도 `hosts` 갱신도 검증할 수
없다. 기계가 생기기 전에는 시작하지 않는다.

## 우회 방지

별도로 떼어 적는다. 이건 기능이 아니라 성격의 문제다.

**"절대 못 하게"는 불가능하다.** 그 Mac의 관리자가 사용자 본인이기 때문이다. 관리자 암호를
아는 사람은 데몬을 내릴 수 있고, 최악의 경우 복구 모드로 부팅하거나 macOS를 다시 깔 수 있다.
이걸 막는 건 회사가 기기를 관리하는 방식(MDM 등록)뿐인데 개인 Mac에는 과하다.

그래서 이런 앱들은 "불가능하게"가 아니라 **"귀찮고 느리게"**를 판다. Cold Turkey나 Freedom의
잠금 모드가 그것이다 — 해제하려면 정해진 시각까지 기다리거나 무작위 문자 수백 개를 쳐야 한다.

지금 뚫리는 순서와 각각의 대응:

| 우회 방법 | 지금 드는 비용 | 막는 방법 |
| --- | --- | --- |
| 앱에서 시간대 삭제 | **클릭 두 번** | 잠금 모드 |
| 규칙 파일 직접 수정 | 텍스트 편집기 | 규칙 파일을 데몬만 쓰는 위치로 |
| `/etc/hosts` 직접 수정 | — | **이미 막힘** (1초 뒤 복구) |
| `launchctl bootout` | sudo 한 줄 | 감시 데몬 쌍 |
| 데몬 파일 삭제 | sudo 한 줄 | `chflags schg` (파일 잠금 플래그) |
| DoH 쓰는 브라우저 | 설정 한 번 | **이미 막힘** (브라우저 정책) |
| 복구 모드 부팅 | 재부팅 | 막을 수 없음 |

첫 줄이 제일 크다. `sudo`까지 갈 필요도 없이 앱에서 클릭 두 번이면 풀린다.

### 할 만한 것

- **잠금 모드** — 규칙에 "언제까지 잠금"을 넣고 그 시각 전에는 데몬이 규칙 변경을 거부한다.
  규칙 파일을 데몬만 쓰는 시스템 위치로 옮기고, 앱은 파일을 직접 쓰는 대신 데몬에 변경을
  요청한다. 지금은 앱이 파일을 직접 쓰는 구조라 이 부분을 바꿔야 한다
- **표준 계정 안내** — 코드가 아니라 사용법이다. 관리자 계정으로 앱을 설치하고 일상은 관리자가
  아닌 계정에서 쓰면 `sudo` 자체가 안 된다. 효과는 위의 어떤 코드보다 확실하고, 대가는 본인이
  자기 Mac의 관리자 권한을 포기하는 것이다

### 하지 않을 것

- **Network Extension** — 운영체제 네트워크 계층에 붙는 필터. 기술적으로 가장 강력하고 DoH도
  걸리지만, Apple이 개별 승인하는 권한이 필요하다. Developer ID조차 없는 지금은 시작할 수 없다
- **MDM 등록** — 개인 Mac에 회사 기기 관리 체계를 씌우는 일이다. 범위 밖

## 어떤 순서로

**2번(차단 중 안내) → 3번(시간대 편집) → 1번(앱 차단)** 을 제안한다.

2번과 3번은 지금 있는 것을 쓸 만하게 만든다. 둘 다 새 권한도 새 의존성도 필요 없고, 데몬과
규칙 구조를 그대로 쓴다. 1번은 그다음이다 — 프로세스 종료라는 새 종류의 위험이 들어오고,
사용자가 저장하지 않은 작업을 날릴 수 있어서 설계를 먼저 정해야 한다.

우회 방지는 **1번이 끝난 뒤**가 맞다. 잠금 모드는 규칙을 누가 쓰느냐를 바꾸는 작업이라, 규칙에
들어갈 것(사이트, 앱, 시간대)이 다 정해진 뒤에 손대는 편이 다시 안 뜯는다.

5번(배포)은 Apple Developer Program 가입 여부에 달렸고, 6번(Windows)은 기계가 있어야 한다.
둘 다 시간이 아니라 조건이 풀려야 시작되는 항목이다.

## 아직 확인 못 한 것

- **Firefox의 DoH** — 이 Mac에 Firefox가 없어 확인하지 못했다. Firefox는 지역에 따라 자체
  암호화 DNS를 기본으로 켜기 때문에, 뚫릴 가능성이 다른 브라우저보다 높다. Firefox는 Chromium이
  아니라 `URLBlocklist` 정책이 안 먹으므로, 뚫리면 따로 막을 방법을 찾아야 한다
- **Aside가 hosts를 어떻게 지나가는지** — 2026-09-03 실측에서 hosts + PF만 걸었을 때 Aside만
  YouTube 실서버에 붙었다(`tv-in-f95.1e100.net:443`). Chrome은 같은 조건에서 막혔고 두 브라우저
  모두 DoH 설정이 비어 있다. 경로를 특정하지 못했다. 지금은 브라우저 정책이 덮고 있어 급하지 않다
