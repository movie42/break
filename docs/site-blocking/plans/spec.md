# 사이트 차단 - 명세

초기 셋업의 `docs/initial-setup/plans/spec.md`에서 정한 규칙 파일 포맷과 스케줄 판정은 그대로 쓴다. 이 문서는 그 판정 결과가 실제 차단으로 이어지는 구간만 다룬다.

## 화면/기능 흐름

- 앱 첫 실행, 데몬 미설치: 상단에 설치 안내를 띄운다. 사이트와 시간대 편집은 설치 없이도 된다
- 설치 버튼 누름: Mac 관리자 암호창이 한 번 뜬다 → 데몬 복사·plist 작성·기동 → 상태가 "실행 중"으로 바뀐다
- 암호창에서 취소: 아무것도 설치되지 않고 상태는 "미설치" 그대로. 오류가 아니라 정상 경로다
- 설치 후 앱 종료: 데몬은 계속 돈다. 차단은 앱 실행 여부와 무관하다
- 재부팅: `RunAtLoad`로 데몬이 자동으로 다시 뜬다
- 차단 구간 진입: 데몬이 `hosts`에 블록을 넣고 DNS 캐시를 비운다. 앱이 떠 있지 않아도 된다
- 차단 구간 종료: 데몬이 블록을 지우고 DNS 캐시를 비운다
- 차단 중 사이트 추가: 저장하면 다음 틱(1초 이내)에 반영된다
- 제거 버튼 누름: 확인을 받고 → 암호창 → `hosts` 블록 제거 → 데몬 정지 → plist·바이너리 삭제
- 제거 중 암호창에서 취소: 아무것도 바뀌지 않으므로 문구 없이 화면만 다시 읽는다. 설치 취소와 달리 안내를 띄우지 않는다

## 화면 문구

코드에 그대로 넣는다. 요약하거나 바꿔 쓰지 않는다.

| 자리 | 문구 |
| --- | --- |
| 데몬 미설치 안내 (2줄) | `차단을 시작하려면 백그라운드 프로그램을 설치해야 합니다.` / `설치할 때 Mac 관리자 암호를 한 번 물어봅니다.` |
| 설치 버튼 | `차단 프로그램 설치` |
| 제거 버튼 | `차단 프로그램 제거` |

| 설치 실패 | `설치에 실패했습니다: {오류}` |

## 상태 정의

### 데몬 상태

| 상태 | 판정 근거 | 화면 |
| --- | --- | --- |
| 미설치 | plist 파일 없음 | 설치 안내와 설치 버튼 |
| 설치됨·정지 | plist는 있으나 `launchctl print`가 프로세스를 못 찾음 | 상태 표시와 제거 버튼 |
| 실행 중 | `launchctl print`가 프로세스를 보여줌 | 상태 표시와 제거 버튼 |

### 규칙 상태

초기 셋업에서 정한 규칙 없음 / 대기 / 차단 구간을 그대로 쓴다. "실행 불가"는 없앤다 — 사용자 권한으로 차단을 시도하는 경로 자체가 사라지기 때문이다. 데몬이 없어서 차단이 안 되는 상황은 위의 데몬 상태로 표시한다.

## hosts 블록 형식

데몬이 관리하는 구간을 마커로 감싼다. 마커 밖은 어떤 경우에도 건드리지 않는다.

```
# BEGIN Break — 이 블록은 Break가 관리합니다. 직접 고치지 마세요.
127.0.0.1	youtube.com
127.0.0.1	www.youtube.com
::1	youtube.com
::1	www.youtube.com
# END Break
```

- 규칙 파일에는 `www.`가 떨어진 호스트만 저장된다(초기 셋업의 정규화 규칙). `hosts`에는 `www.` 붙은 줄을 같이 쓴다 — 사용자가 `youtube.com`을 넣었을 때 `www.youtube.com`도 막히는 게 기대 동작이다
- IPv6(`::1`) 줄도 같이 쓴다. IPv4 줄만 있으면 브라우저가 IPv6 주소를 물어봤을 때 실제 서버로 나간다
- 서브도메인은 막지 않는다. `youtube.com`을 넣어도 `m.youtube.com`은 열린다 — `hosts`는 와일드카드를 지원하지 않는다. 하위 도메인까지 막으려면 사용자가 따로 추가해야 한다
- 블록이 비어야 할 때는 마커까지 통째로 지운다. 빈 마커를 남기지 않는다

## 조정 루프

데몬은 1초마다 아래를 한다. 상태를 메모리에 들고 있지 않고 매번 파일에서 다시 읽는다.

1. 규칙 파일을 읽는다
2. 지금 시각이 차단 구간인지 판정한다 (`break_core::schedule`)
3. 있어야 할 `hosts` 내용을 계산한다 — 차단 구간이면 사이트 목록으로 블록을 만들고, 아니면 블록 없음
4. 현재 `/etc/hosts`를 읽어 3번과 비교한다
5. 다르면 쓰고 DNS 캐시를 비운다. 같으면 아무것도 하지 않는다

이 방식이면 사용자가 `hosts`를 직접 고쳐도 다음 틱에 되돌아오고, 데몬이 재시작해도 상태 복원 절차가 따로 필요 없다.

## 엣지 케이스

- **규칙 파일이 없음**: 차단 없음으로 보고 블록을 지운다. 앱을 지웠는데 차단이 남는 상황을 막는다
- **규칙 파일이 깨진 JSON**: `break-core`의 기존 처리(격리 후 빈 규칙)를 그대로 쓴다. 데몬은 root라 격리 파일이 root 소유로 생긴다 — 다음 저장 때 GUI가 원본 경로에 새로 쓰므로 문제되지 않는다
- **`/etc/hosts` 쓰기 거부**: `Error::NotPrivileged`. 데몬은 root라 정상적으로는 일어나지 않지만, 개발 중 sudo 없이 실행한 경우가 여기다. 로그에 남기고 다음 틱에 다시 시도한다
- **사용자가 마커 블록만 지움**: 다음 틱에 복구된다
- **사용자가 마커 밖 줄을 고침**: 그대로 둔다. `strip_block`은 마커 사이만 잘라낸다
- **마커 시작만 있고 끝이 없음**: 시작 마커부터 파일 끝까지를 관리 블록으로 보고 잘라낸다. 절반만 남은 블록이 계속 쌓이는 것보다 낫다
- **데몬이 죽음**: `KeepAlive`로 launchd가 다시 띄운다. 다시 뜨는 사이 몇 초 동안은 `hosts`가 마지막 상태로 남는다
- **데몬을 지웠는데 차단이 남음**: 제거는 `hosts` 블록을 먼저 지우고 그다음에 바이너리를 지운다. 순서를 어겨 남았을 때의 수동 복구는 `README.md`
- **설치 중 암호 취소**: `osascript`가 `-128` 오류를 반환한다. 실패가 아니라 취소로 구분해 다르게 안내한다
- **데몬 바이너리가 보호 폴더에 있음**: macOS는 `~/Documents`, `~/Desktop`, `~/Downloads`를 접근 보호(TCC) 대상으로 두고, root도 예외가 아니다. 개발 중 프로젝트가 `~/Documents` 아래에 있으면 암호로 올린 셸이 `target/debug/break-daemon`을 읽지 못해 `cp`가 거부된다. 앱이 바이너리를 임시 폴더에 먼저 복사하고 root는 거기서 가져간다 — plist와 같은 방식이다. 승격된 셸은 `cd /`로 시작한다. 보호 폴더에 서 있으면 `getcwd`부터 실패한다
- **홈 디렉토리 경로에 공백**: 설치 스크립트에 넘기는 경로는 작은따옴표로 감싸고 이스케이프한다
- **사용자 계정이 바뀜**: plist에 박힌 규칙 파일 경로가 이전 계정을 가리킨다. 다시 설치해야 한다. 지원 범위 밖으로 두고 문서에만 적는다
- **차단이 걸릴 때 브라우저가 이미 열려 있음**: 그 브라우저에서는 한동안 사이트가 계속 열린다. `dscacheutil -flushcache`는 운영체제 캐시만 비우고, 브라우저가 자기 안에 들고 있는 주소 캐시와 유지 중인 연결은 건드리지 못한다. 브라우저를 껐다 켜면 적용된다. 앱에서 브라우저를 끄는 것은 이번 작업의 범위가 아니다
- **시스템 시각이 뒤로 점프**: 매 틱 현재 시각을 다시 읽으므로 별도 처리가 없다 (초기 셋업과 동일)

## 알려진 한계

- **DNS-over-HTTPS**: 브라우저가 운영체제의 이름 해석을 건너뛰고 자체 암호화 DNS 서버에 직접 물어보면 `hosts`가 무시된다. Safari·Chrome·Aside에서는 우회가 없는 것을 확인했다. Firefox는 이 Mac에 없어 확인하지 못했다 — 뚫리면 방화벽(PF) 작업을 별도 계획으로 잡는다
- **이미 열려 있던 브라우저**: 차단이 걸려도 그 브라우저에서는 한동안 사이트가 열린다. 껐다 켜야 적용된다
- **우회 방지 없음**: 사용자가 데몬을 제거하거나 규칙 파일을 지우면 차단이 풀린다. 이번 작업의 범위가 아니다
- **서브도메인·IP 직접 접속**: `hosts`로 막을 수 없다
